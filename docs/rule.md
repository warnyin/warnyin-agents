# Rule — Warnyin Standard Workflow (repo เอง)

> กฎระดับโปรเจกต์ของ repo มาตรฐานนี้ (ไม่ผูกกับ component เดียว) · SHIP promote rule ใหม่เข้ามาที่นี่
> rule ที่ผูกกับ component เฉพาะ → อยู่ใน `docs/techstack/<component>/rule.md`

## 1. ปรัชญาแก่น (จาก CLAUDE.md + roadmap)
- **กระทัดรัด opinionated** — 5 stage + role จำกัด เป็นจุดแข็ง ห้ามไหลเป็น catalog
- **tool-agnostic** — แก่นเป็น `.md` กลางที่ทุก harness อ่านได้ (`.warnyin/workflow/`); ส่วนที่ผูก tool (hook/skill) เป็น *adapter บาง* ชี้กลับแก่น
  - **payload-guidance ต้อง generic** (enforce ของ tool-agnostic) — guidance ใด ๆ ใน payload ที่อ้าง **model/tooling ของ harness** (เช่น model-tier ใน `contexts/`) ต้องใช้ **vocab generic** (`deepest reasoning`/`balanced`/`cheap`) **ไม่ผูกชื่อรุ่น/ผลิตภัณฑ์** (Claude/Opus/GPT/Gemini/...) — แต่ละ harness map เอง; **แม้ในประโยคปฏิเสธก็เลี่ยง enumerate ชื่อรุ่น** (กัน grep tool-agnostic false-positive); เป็น **guidance ไม่ enforce**. **การ map tier→ชื่อรุ่นจริงทำที่ adapter (`.claude/`) เท่านั้น** — payload (`.warnyin/`) ส่งต่อ vocab generic, adapter (เช่น `command/build.md`) อ่านแล้ว map เป็นชื่อรุ่นของ harness ก่อนส่งเข้า runtime; evidence: topic `improve-performance` (model routing per-task — command map, `build-wave.mjs` pass-through generic)
  - **skill-adapter convention** (enforce ของ "adapter บาง") — Claude skill (`.claude/skills/<name>/SKILL.md`) = adapter บาง **ชี้ playbook กลาง ไม่ duplicate** (เหมือน command); ทำ **auto-invocable เฉพาะ utility read-only safe** (ไม่ใส่ `disable-model-invocation`) เพื่อคุม blast radius; **irreversible/stateful (build/ship/design ฯลฯ) คงเป็น command** (user-only — ต้อง user สั่งชัด); **ไม่แปลง package เป็น plugin** (รักษา namespace `/warnyin:*` ของ command = non-breaking; skill ยอมรับ `/<name>` ไม่มี prefix) — auto-invoke เป็น description-driven (ไม่มี event/file-watch)
- **ห้ามเดา** — ไม่ชัดถาม user; enforce ด้วย rule/checklist ใน playbook
  - **investigate-before-edit** (enforce ของ "ห้ามเดา") — ก่อนแก้ไฟล์ที่มีอยู่ ต้องเข้าใจก่อน: **ใครใช้/อ่านไฟล์นี้, schema/contract/สัญญาของมัน, เจตนาเดิม**; แก้โดยไม่เข้าใจ = เดา (ไม่ชัด → ถาม user / อ่านโค้ดที่อ้างถึง ก่อนแก้) — อยู่ใน BUILD/VERIFY playbook §3 + developer.md/qa.md checklist
  - **config-protection** (enforce ของ "ห้ามเดา") — ห้ามแก้ config (linter/formatter/test threshold) หรือ disable rule **"เพื่อให้ build/test ผ่าน"** แทนการแก้โค้ดจริง; config ผิดจริงแก้ได้แต่ต้องมี **เหตุผลชัด + note** (ไม่ใช่เพื่อเลี่ยง finding) — สำคัญสุดตอน VERIFY fix loop ("แก้จนผ่าน" = แก้ root cause ไม่ลด bar)
- **context (session) ⊥ role (task) — คนละชั้น ห้าม duplicate** — `contexts/` = session-level posture (โหมดทั้ง session: research/build/review), `roles/` = task-level lens (บทบาทต่องาน); context อยู่ `.warnyin/workflow/contexts/` โครงบาง **ชี้กลับ playbook ไม่ copy checklist** ของ stage/role (single source of truth); เพิ่ม context = เพิ่มไฟล์ + callout ใน stage ที่เข้าคู่ + ตารางใน `contexts/README.md` — เก็บ opinionated (3 ตัวพอ ไม่เป็น catalog)
- **ทุก stage playbook ชี้ context ที่เข้าคู่** — แต่ละ `stages/*.md` มี callout `Context profile` ใต้ title (Discovery→research · DESIGN→research+build · BUILD→build · VERIFY→review · SHIP→review); เพิ่ม stage ใหม่ต้องระบุ context posture ของมัน
- **continuous-learning discipline** (คู่ "ห้ามเดา") — ความรู้/บทเรียนที่ได้ **ตอนทำจริง** (BUILD/VERIFY) ไม่ใช่แค่ตอนวางแผน → จับเป็น **learned-rule ที่ SHIP** ด้วย `rule (generalize) + evidence (บังคับ) + scope (component/project)` แล้ว **user ยืนยัน** ก่อน promote (กลไกใน `stages/ship.md` §3-§6 — unify กับ note "รอ SHIP"); learned-rule = กฎ generalize **ไม่ใช่ incident** (troubleshooting = incident ที่อ้างเป็น evidence ได้) — ยืมแก่น instinct แบบ manual ไม่มี runtime observer
- **unify-in-place ไม่สร้างกลไกขนาน** — เมื่อเสริม mechanism ที่ **ทับซ้อนกับของเดิม** ให้ **ขยายในที่เดิม** (เช่น ขยาย principle/gate item เดิม ให้ของเก่ากลายเป็น subset) แทนการเพิ่มข้อ/สร้างกลไกใหม่ขนานกัน — กัน bloat + สับสน (สอด "กระทัดรัด opinionated"); หลักฐาน: #6/#7/#8 ขยาย playbook §3/§6 ในที่เดิมทุกครั้ง
- **canonical-copy convention** (enforce ของ "single source of truth") — ความรู้/wording ชุดเดียวที่ต้องกระจายหลายไฟล์ (เช่น กติกา merge ของ Spec delta ใน playbook+template+command) ต้อง **นิยาม canonical ไว้ที่เดียวใน `design.md` ของ topic แล้ว copy ไปทุกไฟล์ — ห้ามแต่งใหม่ต่อไฟล์**; กติกาเต็มอยู่ playbook เดียว ที่เหลือเป็น pointer บาง — evidence: topic `feature-spec-delta` (panel B2 บังคับ normalize พิกัด + VERIFY T3 ผ่าน semantic check คำต่อคำเพราะกติกานี้); **หลัง merge branch ข้ามสายที่แตะไฟล์เดียวกับ block ที่เพิ่ง refactor → rerun เช็ค canonical/single-source (falsifiable grep) เสมอ** — conflict resolution อาจเก็บเนื้อเก่าฝั่ง branch ทับ block ใหม่เงียบๆ โดย full gate (test/lint/pack) เขียวหมดไม่จับ (regression ระดับ wording ไม่ใช่ link/test) — evidence: topic `build-lean` (verify F1: merge `release/0.23.0` คืน theory block เก่าเข้า `verify.md`; จับได้ด้วย negative-grep single-source — KB TS-4); **★ contract ที่ถูก copy ข้ามไดเรกทอรีต้องระบุ path variant ต่อไฟล์ ไม่ปล่อยให้ผู้ copy คำนวณเอง** (pointer resolve จากที่อยู่ของ**ไฟล์ผู้ชี้** — `./x.md` จาก `stages/` ชี้คนละที่กับจาก root) และ **string ที่ถูก assert คำต่อคำชนะ pattern ประจำไฟล์เสมอ** — copy เหมือนกันทุกไฟล์แม้ไฟล์ปลายทางมีสไตล์ของตัวเอง ("จัดให้เข้า pattern" = paraphrase → string-equality แดง + wording drift 2 ที่) — evidence: topic `project-memory` (panel B4 → แตก C3 เป็น C3a/b/c ต่อไฟล์; T4 copy C7 ลง `codebuddy-rules.md` ทั้งที่ไฟล์นั้นปกติตัด path ในวงเล็บ)
- **build-orchestration: commit topic docs ก่อน fan-out** — BUILD orchestrator ต้อง commit `docs/stages/<slug>/` ลง build branch **ก่อน** fan-out worktree agent — agent จะเห็น task ของตัวเองครบ; สถานะ/บันทึกใน topic dir ที่ agent แก้ไม่ได้จาก worktree → **main loop อัปเดตตอน integrate** (ห้ามถือว่า task ล้ม). **กลไก sync (implemented):** harness fork worktree จาก main (คุมไม่ได้) → `build-wave.mjs` รับ arg `baseRef` (ชื่อ build branch) แล้ว prompt สั่ง agent `git merge <baseRef>` step แรกก่อนอ่าน task (abort-on-conflict + hard-stop ถ้า task.md ไม่ปรากฏ + retry transient lock); orchestrator ส่ง `baseRef` + integrate ด้วย `git checkout <branch> -- <scoped src files>` (เลี่ยง topic-docs copy, ปลอด KB#11) — evidence: topic `feature-spec-delta` TS-1 + `validator-status` TS-2 (ปัญหา) → `build-wave-branch-fix` (แก้กลไก)
  - **★ กฎที่ต้องถึง sub-agent ที่ถูก fan-out ต้องอยู่ใน root doc ไม่ใช่แค่ capability playbook** — `build-wave.mjs` prompt สั่ง sub-agent อ่านแค่ role card + 4 ไฟล์ task + techstack rule → **playbook กลางไปไม่ถึง**; กติกาที่ agent ใน worktree ต้องรู้ (เช่น "worktree agent ห้ามเขียน project memory เอง") ต้องทวนไว้ใน **root doc ที่ auto-load ทุก agent** (`CLAUDE.md`/`AGENTS.md` template) แบบ **คำสั่งสั้น ไม่ใช่กฎเต็ม** (canonical ยังอยู่ที่ playbook); คู่กับ **hook ของ stage ที่มี fan-out ต้องมี main-loop-only variant แยกชัด** — stage ที่ fan-out worktree (BUILD) ต้องระบุว่า **ใครเป็นคนเขียน artifact ที่ใช้ร่วมกัน** ไม่งั้น sub-agent เขียนทับกัน — evidence: topic `project-memory` (panel Sec-B3 → C6 root-doc note + C2b hook `main loop เท่านั้น`)
  - **★ src→root sync-gap (improve-performance TS-1):** root dogfood (`.warnyin/`, `.claude/`) ถูก gitignore → **canonical tracked = `src/` เท่านั้น**; รัน workflow/script จาก root (เช่น `.warnyin/workflow/scripts/build-wave.mjs`) ใช้เวอร์ชัน **เก่ากว่า `src/` จนกว่า release sync src→root** → worktree mode ต้องมั่นใจ script มี `baseRef` (จาก `src/`) + ส่ง `baseRef`, หรือ fallback `isolate:false` (shared-tree, agent ทำใน working tree จริง) ใน repo ที่ root playbook ถูก gitignore — อย่าแก้ไฟล์ root โดยตรง (git ไม่เห็น)
- **structural validator: ✖ ไม่พึ่ง filled-detection** — gate/validator ที่เช็คโครงเอกสาร: เช็คระดับ **✖ (block) ต้องเป็น existence/structure ล้วน** (deterministic — เช่น ไฟล์มีครบไหม, ตารางมี data row ไหม, spec มี Requirement/Scenario ไหม); เช็คที่พึ่ง **heuristic เดา "artifact เติมแล้วหรือยัง"** (เช่น H1 ไม่มี placeholder) ต้องเป็น **⚠ best-effort เท่านั้น ไม่ block** — heuristic หยาบ ยอมรับ false ได้ ห้ามเอามาตัดสิน ✖; evidence: topic `validator-status` design review B1 (`const FILLED_MARKERS` เปราะ → เปลี่ยนเป็น H1-heuristic + demote C1/C4 เป็น ⚠) + `validate-topic.mjs` §4.2; **mode inference (lean/fast mode) ต้อง fail-safe ไปทาง full checks** — เงื่อนไขเข้า mode ที่ลดเช็คต้องเป็น conjunction ชัดเจน (ทุกข้อจริง) และสถานะก้ำกึ่ง/ปนกัน → รันเช็คเต็ม + ⚠ บอกผู้ใช้ ไม่ข้ามเช็คเงียบๆ (การข้ามเช็คผิดตัวอันตรายกว่าเช็คเกิน — ทิศ fail เดียวกับ change-sizing "ก้ำกึ่ง → ปัดขึ้น standard") — evidence: topic `build-lean` (validator fast-mode: conjunction 3 ข้อ + mixed-state → full checks + ⚠ C6)
- **worked-example convention** (enforce ของ "tool-agnostic / ไม่ duplicate") — เอกสารตัวอย่างสอนผู้ใช้ (เช่น `docs/example-walkthrough.md`) ต้อง (1) **surface achieved topic จริง — ชี้กลับ ไม่ duplicate** เนื้อหา (เหมือน command/skill ชี้ playbook), (2) มี **disclaimer snapshot + pointer ไป playbook source** (`src/.warnyin/workflow/stages/`) กัน narrative drift เมื่อโครงเปลี่ยน, (3) **ไม่ ship npm** (อยู่ `docs/` นอก `files` — ผู้ใช้ดูบน repo), (4) **ลิงก์ playbook ชี้ `src/.warnyin/`** (committed source) ไม่ใช่ root `.warnyin/` (dogfood gitignored → ไม่ resolve บน GitHub); เน้นเล่า **decision/เหตุผล** ไม่ใช่ลอกขั้นตอน — maintenance ต่ำ + กัน staleness
- **DAG-width ก่อน serialize (DESIGN)** — แตก task แล้ว **วัด critical-path depth + max wave width** ของ DAG เสมอ ก่อนปิด DESIGN; ถ้าได้ chain เส้นตรง (ทุก wave 1 task) ต้องมี **เหตุผล explicit** ว่าทำไม decouple ไม่ได้ (กัน chain เผลอ = ต้นเหตุ BUILD ช้า "1 agent/wave"). toolkit ลด serialization (optional เลือกตามเคส คงนิยาม vertical slice เดิม): **contract-first decouple** (task พึ่ง contract/stub ของอีก task ไม่ใช่ runtime → ขนานได้, พิสูจน์ integration ที่ full-gate) · **re-slice ต่างแกน** · **ยอม serialize เฉพาะ chain แท้** แล้วลดเวลา node บน critical path (model tier per task + task/context lean). เป็น **judgment gate** (reviewer ตีความ ไม่ใช่ mechanical check ของ `validate-topic`); เร่งเวลา node ด้วย **model routing per task** (tier `Model tier` ใน `task.md`) + **lean self-verify** (agent verify scope component ตัวเอง — integration เลื่อนไป full-gate, ไม่รันซ้ำต่อ task) — evidence: topic `improve-performance` (design §3A/§3B/§3D + empirical: scaffold chain depth 4 → redesign wave width 2, งานเอง wave width 3); **release-hygiene task (CHANGELOG/bump/gate integration-level เช่น `lint:md`) เป็น wave สุดท้ายเสมอของ topic multi-slice** — gate ที่ต้องเห็นไฟล์/pointer ครบข้าม slice ต้องรันหลัง integrate ครบ (กัน false-negative จาก pointer ข้าม slice + กัน CHANGELOG เขียนก่อนรู้ผลจริง) — evidence: topic `build-lean` (design §6/§7 dead-link integration gate)
- **Parallelize gathering, serialize judgment/narrative (หลักการแกน fan-out ใน stage)** — fan-out read-only sub-agent เพื่อ **"เก็บข้อมูล / เขียนหน่วยที่ independent"** ได้ (grounding หลายโดเมน, research ก่อนเขียน design, เขียนไฟล์ task แต่ละใบที่อยู่คนละโฟลเดอร์) แต่ **"การตัดสิน scope + เขียน narrative ที่ต้อง coherent"** (`proposal.md`/`design.md`) คงเป็น **single-writer (main loop)** — แตก narrative ให้หลาย agent เขียนคนละ section → ต่อไม่เนียน → review+rewrite แพงกว่าเขียนรอบเดียว; **ทุกจุด fan-out ต้องมี fallback** "เครื่องที่ fan-out ไม่ได้ → ทำตามลำดับเหมือนเดิม" (tool-agnostic). เป็น **กรอบร่วม** ของ DAG-width toolkit + review panel fan-out + task-file fan-out — **ขยายในที่เดิม ไม่ใช่กลไกใหม่ขนาน** (สอด unify-in-place); คู่กับ "DAG-width ก่อน serialize" (ลด serialization ของ task-DAG) — ข้อนี้ตอบ "fan-out เมื่อไหร่/ที่ไหน". evidence: topic `parallel-design-docs` (`design.md` §3 หลักการแกน + §4 step 2/5/9 + build 2 task ขนานจริง; feature `build-orchestration` #6-8)
- **stage-invoked capability convention** (enforce ของ "กระทัดรัด opinionated / tool-agnostic / ไม่ duplicate") — capability doc ที่ **stage เรียกเองแบบ conditional (auto-detect)** ต่างจาก utility skill/command ที่ user/model เรียกตรง — ต้อง (1) มี **detect section ที่ระบุ "ไม่เข้าเงื่อนไข → ข้าม" ชัด** (adaptive ไม่ยัดเยียด topic ที่ไม่เกี่ยว), (2) **ทุก gate item ที่เพิ่มในแต่ละ stage ต้อง conditional/N-A** (backward compatible — ไม่ block topic ที่ capability ไม่เกี่ยว), (3) **logic อยู่ใน capability doc เดียว; stage ชี้กลับด้วย pointer + เลข section ไม่ duplicate** (canonical-copy), (4) **tool-agnostic** — detect-in-playbook (ทุก harness ได้) ไม่ใช่ description-trigger ของ skill; เครื่องมือภายนอกอ้างอิงแบบ **reference ไม่ vendor**; เพิ่ม capability แบบนี้ = เพิ่มไฟล์ใน `.warnyin/workflow/` + hook บางใน stage ที่เข้าคู่ + ระบุใน `workflow/README.md` — **evidence:** topic `adaptive-api-doc` (`api-doc.md` §2 detect+skip + gate conditional 3 stage + pointer §2/§4; verify T1-T5 ผ่าน) · **generator variant** — topic `uxui-wireframe` พิสูจน์ sub-pattern ที่ capability **fan-out read-only generator** (`warnyin-ux` คืน artifact เป็น text → main loop persist, single-writer) + **approve gate** (user ยืนยัน artifact) ก่อน conditional gate item — ต่างจาก api-doc (doc-producer ล้วน); hook อยู่ใน DESIGN เดียว (`design.md` §4 step 4.5 + detect + §8 gate + §3 role lens/panel note); canonical wording copy จาก design ของ topic (achieved 2026-06-13)

## 2. Engineering rules
- **zero-dependency** — `devDependencies` ต้องว่างเสมอ; ทุกเครื่องมือใช้ built-in `node:*` (test = `node:test`) — เหตุผล: กระทัดรัด + ไม่มี supply-chain risk (จุดขายของ tool)
  - **zero-dep lint-gate convention** (enforce ของ zero-dependency) — งาน lint/format/quality-gate ของ repo เอง ทำเป็น **`node:*` script เขียนเอง** (pure function + main-guard + CI job) **ไม่เพิ่ม devDeps** (เช่น markdownlint/prettier/eslint) — pattern เดียวกับ `verify-pack.mjs`/`check-test-count.mjs`/`lint-md.mjs` (dead-link gate); gate ต้อง **testable** (pure fn รับ input + injectable IO → unit feed ปลอม) + **executable verify** (รันจริงจับเคส positive/negative ไม่ใช่แค่ unit) — ถ้าต้องการ rule เยอะแบบ tool มาตรฐาน ให้ชั่งกับ "ทำลาย zero-dep" ก่อนเสมอ (default = เขียนเอง เฉพาะ high-signal)
- **ESM** — repo `type: module`; ใช้ `import`/`export`, `import.meta.url` ไม่ใช่ `__dirname`/`require`
- **ภาษา:** คอมเมนต์/ข้อความผู้ใช้เป็นภาษาไทย ตามสไตล์ `src/bin/cli.mjs`
- **CHANGELOG ทุก user-facing change** — bump `engines`, breaking, เปลี่ยนพฤติกรรม installer → ต้องมี entry ใน `CHANGELOG.md` (Keep a Changelog) ให้ผู้ใช้ npm migrate เองได้โดยไม่ต้องเดา
- **npm scripts (dev tooling) ต้อง cross-platform** — เป็น **node script** (`node src/scripts/*.mjs`) ไม่ใช่ shell oneliner ที่ผูก POSIX; ใช้ `os.tmpdir()`/`path.join` (ห้าม hardcode `/tmp`, `/`), spawn array args ห้าม `shell:true` (ยกเว้น npx บน win32 ที่เป็น `.cmd`); เผื่อ Windows npx bin-shim resolve ไม่ได้ → ต้องมี fallback หรือ exit error ชัดเจน
- **executor-playbook convention** (enforce ของ "unify-in-place / canonical-copy / ไม่ duplicate") — playbook ที่ **เดินกฎของ playbook อื่น end-to-end** (เช่น `fastlane.md` เดิน fast-track skip-list ของ `triage.md`) ต้องเป็น **orchestration ล้วน** (ลำดับ step + gate + escalation + resume) + **pointer-per-row** ชี้กลับเจ้าของกฎ — **ห้าม inline เนื้อกฎ** (ทั้งตารางและ prose) เพราะจะเกิด policy drift 2 ที่; พิสูจน์ได้ด้วย **negative-grep** string เอกลักษณ์ของ canonical (ต้องเจอในไฟล์เจ้าของไฟล์เดียว) — evidence: topic `fastlane` (`fastlane.md` §3 pointer-per-row + test `fastlane.test.mjs` B2/B3; feature `docs/features/fastlane/`)
- **anchor-immutability** (enforce ของ "ห้ามเดา" + link integrity) — heading ที่มี **inbound markdown-link ≥2 ไฟล์** ถือเป็น **public API ของ playbook** — เปลี่ยน/rename ได้เฉพาะเมื่อแก้ inbound ทุกจุดพร้อมกัน; เหตุผล: `lint-md.mjs` **ตัด anchor ทิ้งก่อนเช็ค** (จับ dead path ไม่จับ dead anchor) → เปลี่ยน heading = ลิงก์พังเงียบ (เช่น `#fast-track-skip-list` ถูกอ้าง 5 ไฟล์); anchor link (`#...`) ที่ critical ควรมี **เคส structural ใน test suite** (slugify heading เอง แล้ว assert) — evidence: topic `fastlane` (test C1; troubleshooting anchor)
- **contract-as-copy-source** (enable task fan-out ขนาน) — เมื่อหลาย task ใน wave เดียวต้องเขียน wording ที่ถูก assert ด้วย **string-equality**, ให้ยกข้อความ canonical ไว้ใน `design.md §4` (contract) แล้วให้ task **copy คำต่อคำ** — ไม่ให้ task อ่านไฟล์ปลายทางของ task อื่น; เหตุผล: ตัด read-dependency ระหว่าง task → ขนานใน wave เดียวได้จริง (ไม่ต้อง serialize รอ task อื่นเขียนเสร็จ) — evidence: topic `fastlane` (wave 1 playbook+wiring ขนานจริง; `design.md §4` C1-C18)
  - **★ contract ตัดได้แค่ read-dependency ไม่ตัด runtime dependency → slice ต้องเป็นเจ้าของ artifact ที่เทสของตัวเองพึ่งพา** — ถ้าเทสของ slice หนึ่งต้องอ่าน **ผลลัพธ์รันไทม์** ที่มาจากไฟล์ของอีก slice (เช่น เทส installer `runCli()` แล้วอ่านไฟล์ที่ seed มาจาก template) ให้ **ย้าย ownership ของ artifact นั้นมาอยู่ slice เดียวกับเทส** แทนการใส่ existence-guard ข้าม task (guard = เทส vacuous ที่เขียวโดยไม่ได้ทดสอบอะไร) — DAG ยังขนานเท่าเดิม; evidence: topic `project-memory` (ย้าย `template/docs/*` จาก T1 → T3 หลัง coherence check; DAG คงเดิม depth 2 / width 5)
  - **★ assertion ที่นับ exact-set ของไฟล์ด้วย compound-needle ต้องมี constraint ผูกที่ task เจ้าของไฟล์ canonical ด้วย** — needle ที่ใช้ "ข้อความของ hook" ระบุไฟล์ที่ **มี** hook จะแยกไม่ออกจากไฟล์ที่ **นิยาม** hook (playbook canonical พูดถึง hook เดียวกันโดยธรรมชาติ → กลายเป็นไฟล์เกิน → gate แดงหลัง integrate); builder ของ wave 1 มองไม่เห็นไฟล์เทสของ wave 2 จึงต้องเขียน constraint ลง `task.md`/`spec.md` ของ task เจ้าของ canonical — คู่กับ **wave ที่ decouple ด้วย contract ต้องประกาศไว้ใน task file ว่า gate ไหนยังรันไม่ได้ในรอบนั้น** (เช่น dead-link ที่พึ่งไฟล์ของ task อื่น = หน้าที่ของ release-hygiene wave) กัน build agent เสียเวลาหรือแย่กว่านั้นคือ**แก้ contract เพื่อให้ gate ผ่าน** — evidence: topic `project-memory` (KB TS-3 + constraint A4b ของ T1; `stage-wiring` ประกาศ lint:md เป็นของ wave 2)

## 3. Security baseline
> security 2 มิติ: **CI/pipeline** (3.1) + **การรัน AI agent ในเครื่อง** (3.2) — payload ของ workflow ถูก agent execute ต่อ จึงเป็น surface ทั้งคู่

### 3.1 CI security baseline (บังคับทุก workflow ใน `.github/workflows/`)
> ถ้าผิดหลายข้อพร้อมกัน = pwn-request / supply-chain risk
- `permissions: contents: read` ที่ top-level (least-privilege)
- trigger `pull_request` — **ห้าม `pull_request_target`** (job รันโค้ดจาก PR)
- **ไม่มี `secrets.*`** เว้นจำเป็นจริง (เพิ่ม publish/token ต้องผ่าน review แยก)
- pin action ด้วย commit SHA (+ คอมเมนต์เวอร์ชัน)
- **ไม่ตั้ง `npm ci`/`cache: npm`** ตราบที่ repo zero-dep (ไม่มี lockfile → จะ fail)

### 3.2 Agent-runtime security baseline (การรัน AI agent ในเครื่อง — guidance portable)
> tool-agnostic principle; รายละเอียด + Claude adapter note ใน `roles/security.md` section "Runtime / operational security" · ไล่เช็คตอน DESIGN panel + VERIFY (รัน local env ที่มี secret จริง)
- **secret isolation** — agent ไม่ควรเข้าถึง secret นอก scope งาน (`.env`, `~/.ssh`, credential/token, keychain); least-privilege ระดับ filesystem
- **no unnecessary egress** — payload/skill ที่ agent execute ต่อ จำกัด egress เท่าที่งานต้องใช้ (sandbox/network restriction)
- **identity separation** — ไม่ใช้ credential ส่วนตัว/prod ใน session ที่รัน automation/agent; แยก scoped identity
- **supply-chain** — third-party skill/MCP/payload `.md` = prompt-injection surface (โค้ด+instruction ที่ AI execute ต่อ) → ตรวจเนื้อหาก่อนติดตั้ง, ติด global ไม่ vendor เข้า repo, จำกัดสิทธิ์

## 4. Installer / packaging rules
- **installer สร้าง scaffold เอง — ห้าม copy พื้นที่ทำงานจาก repo ต้นทาง** — workspace ที่ผู้ใช้เป็นเจ้าของ (`docs/stages/`) ต้อง generate ใน target ไม่ลากของ repo ต้นทางไป (กัน scaffold leak → ดู `troubleshooting.md` #1)
- **pack-verify เป็น gate ก่อน publish + testable** — assert payload ติด tarball **และ** ไม่มีงานจริง/ไฟล์รั่ว (`docs/`, `src/tests/`, `src/scripts/`, `.github/`, installed dogfood ที่ root) หลุดขึ้น package; แยก pure `checkFiles(files)→errors[]` + unit พิสูจน์ denylist จับได้จริง (กัน gate ลวง)
  - **★ existence-gate ต้อง assert ทุกก้อนของ payload ที่ผู้ใช้ต้องได้ ไม่ใช่แค่ก้อนที่เคยพัง** — gate ที่ assert เฉพาะ prefix ที่เคยหลุดในอดีตจะปล่อยก้อนใหม่หายเงียบ (เช่น `src/.warnyin/template/` หายจาก tarball → ผู้ใช้ได้ scaffold เปล่าโดย gate ยังเขียว = **gate ลวง**); เพิ่ม payload ก้อนใหม่ = เพิ่ม required-assert ของก้อนนั้นพร้อม unit negative เสมอ — evidence: topic `project-memory` (T6 เพิ่ม assert `src/.warnyin/template/docs/`)
- **★ payload ที่ติดตั้งลงเครื่องผู้ใช้ต้องถูกคุมที่ "จุดเขียน" ไม่ใช่แค่ "จุด commit"** — gate ที่สแกนเฉพาะ source จะเขียวลวงเมื่อ artifact ที่ runtime ใช้จริงมาจากอีก layer (tarball → target); โดยเฉพาะ **EOL**: `.gitattributes` (`* eol=lf`) เป็นกฎของ **checkout ครั้งหน้า ไม่ใช่ของ working tree ปัจจุบัน** และ `npm pack` แพ็คจาก **working tree ไม่ใช่ index** → checkout ที่เกิดก่อนเพิ่ม `.gitattributes` ยังเป็น CRLF แล้วส่งต่อขึ้น tarball ทั้งก้อน; `.warnyin/workflow/scripts/*.mjs` ถูกส่งผ่าน Workflow tool ที่ **ปัดตก script ที่มี control character** (CR) → `/warnyin:build` ของผู้ใช้พังทั้งระบบ. **แก้ที่ installer: normalize EOL เป็น LF ตอนเขียนทุกจุดที่ copy เนื้อจาก package ลง target** (ไฟล์ binary ไม่แตะ, byte-equal skip เทียบเนื้อที่ normalize แล้ว) + gate ครอบไฟล์ text **ทุกนามสกุล** ใต้ `src/` ไม่ใช่แค่ `.mjs`; เพิ่ม `.gitattributes` แล้วต้อง **renormalize working tree** ด้วย (`git rm --cached -r . && git reset --hard`) — evidence: topic `project-memory` (KB TS-1 · วัดจริง `git ls-files --eol` = `i/lf w/crlf` 812 ไฟล์ · `normalizeEol()` + เทส EOL3/EOL4/EOLI)
- **★ ไฟล์ที่ agent เขียนเอง + commit และอยู่ใน `SCAN_ROOTS` ของ dead-link gate ต้องอ้าง path เป็น inline-code ห้าม markdown-link** — ไฟล์ที่ agent เติมเนื้อหาเองตลอดอายุโปรเจกต์ (เช่น `docs/memory.md`) ถ้าเขียนลิงก์ชี้ `docs/stages/<slug>/` แล้ววันหนึ่ง SHIP `git mv` topic เข้า `achieved/` → `lint:md` **แดงถาวรโดยไม่มีใครแก้โค้ด**; `CODE_RE` strip inline-code ก่อน match → backtick ปลอดภัย 100% — บังคับด้วย **คำเตือนที่หัวไฟล์ template** + เทส "template มี 0 markdown-link" — evidence: topic `project-memory` (`design.md §3.1` + T6 เคส M6b)
- **`package.json files` เป็น allowlist (granular)** — เพิ่ม path ใหม่ต้องคิดว่า publish ไปด้วยไหม; **nested dotfolder ต้องระบุชัดทุกก้อน** (npm ไม่รวมให้อัตโนมัติ — แม้ไม่ใช่ top-level)

## 5. Testing rules
- **test installer = black-box spawn** — spawn `src/bin/cli.mjs` จริงใน temp dir แล้ว assert side-effect (ไฟล์/exit code/stdout/stderr); **ห้าม refactor target เพื่อ testability** + ห้าม import logic จาก `cli.mjs` (มันรัน side-effect ตอน import)
- **harness กลาง** — `makeTempProject(t)` + `runCli(cwd, args)` เป็น test pattern กลางของ repo ใช้ซ้ำทุก test ของ CLI (ดู `docs/techstack/installer/standard.md`)
- assert `code===0` ก่อนเสมอ + surface `stderr` ใน assertion message; assert stream ให้ตรง (`console.warn`→stderr); spawn array args ห้าม `shell:true`
- **acceptance = pass count ไม่ใช่แค่ exit 0** — `node --test` คืน exit ที่หลอกได้ (tests=1 pass=0) → gate ต้อง assert pass count บน CI matrix (ดู `check-test-count.mjs`; `troubleshooting.md` #3)
- **negative fixture ของ keyword-heuristic ต้องเลี่ยง trigger phrase** — เมื่อเทส validator/parser ที่ตัดสินด้วยการ match keyword (เช่น `ไม่มี delta`/`Spec delta`/`GIVEN`), ข้อความ filler ใน **negative fixture ต้องไม่มี keyword นั้นเป็น substring** — ไม่งั้น fixture trigger เคสตรงข้ามโดยบังเอิญ (โค้ดถูก แต่ test แดง/เขียวผิด); test แดงทั้งที่โค้ดดูถูก → สงสัย fixture ก่อน — evidence: topic `validator-status` troubleshooting TS-1 (C4 false-skip จาก filler มี "ไม่มี delta")
- **ห้ามใส่ path/glob arg ให้ `node --test`** ถ้าต้อง portable ข้าม node major — ใช้ bare `node --test` (auto-discover); node 24 ตี path เป็น module, glob `**` ใช้ได้แค่ node 21+ (`troubleshooting.md` #3)
- **verify เอกสาร narrative = accuracy เทียบ source** — เอกสารที่ "เล่าเรื่อง" จาก source อื่น (เช่น worked-example เล่า achieved topic, behavior spec สกัดจาก payload) มีความเสี่ยงเฉพาะ = **misrepresent** (เล่าผิด/แต่งให้ดูดี); VERIFY ต้อง (1) เทส **dead-link** ทุกลิงก์ resolve, (2) เทส **claim ทุกข้อตรงกับ source จริง** (เทียบ build/verify/proposal/ship), (3) **snapshot honesty** — ถ้าตัวเลข/สถานะเปลี่ยนไปแล้ว เอกสารต้องรายงาน **ค่าประวัติ ณ ตอนนั้น** ไม่ใช่ค่าปัจจุบัน (กันเข้าใจผิด), (4) **ตรวจโดย agent อิสระจากผู้เขียน** — self-check ของ build agent ไม่พอ (ผู้เขียนมองข้าม claim ผิดของตัวเอง) — evidence: topic `feature-spec-delta` verify fix #1 (ตรวจอิสระจับ claim `review`→`balanced+` ที่ self-check หลุด)
- **★ structural single-source / anchor check = เคส node ใน suite ไม่ใช่ shell `grep -rl`** — falsifiable check ที่ยืนยัน invariant ของ payload (canonical อยู่ไฟล์เดียว = **negative-grep**; markdown anchor `#...` resolve ไป heading จริง) ต้องเขียนเป็น **เคสใน `node --test`** (อ่านไฟล์ด้วย `node:fs` + walker เอง แล้ว assert) — **ห้ามพึ่ง shell `grep -rl`/`rg` ใน `test.md`/doc** เพราะ (1) รันบน Windows dev ไม่ได้, (2) ไม่เป็นส่วนหนึ่งของ `npm test` → ไม่มีใครรันจริงตอน CI → regression ของ canonical/anchor หลุดเงียบ; **anchor ต้องเช็ค structural เอง** (slugify heading แล้วเทียบ) เพราะ `lint-md.mjs` ตัด anchor ทิ้งก่อนเช็ค (จับ dead path ไม่จับ dead anchor) — evidence: topic `fastlane` (`fastlane.test.mjs` B1-C1 ย้าย single-source/anchor check เข้า suite; คู่กับ `anchor-immutability` §2)

## 6. Bootstrap / self-hosting (2-layer)
> repo นี้ dogfood ตัวเองด้วย release เสถียร (เทียบ compiler ที่ compile ตัวเองด้วยเวอร์ชันก่อน) — ดู `docs/project.md`, `docs/infra.md`
- **source/dogfood แยกชั้นเด็ดขาด** — source ของ warnyin v-next อยู่ `src/**` (committed, publish) เท่านั้น; root `.warnyin/`/`.claude/{commands/warnyin,agents}`/`CLAUDE.md`/`AGENTS.md` เป็น **dogfood ที่ install จาก release และ gitignored** — ห้าม commit (กันแก้ workflow แล้วพังกลางงาน)
- **`.gitignore` ของ dogfood ต้อง root-anchored (`/` นำหน้าทุกบรรทัด)** — เช่น `/.warnyin/` ไม่ใช่ `.warnyin/` ลอย ๆ. git: pattern **trailing-slash อย่างเดียว** (เช่น `.warnyin/`, `.claude/`) match ที่ **ทุก depth** → จะโดน `src/.warnyin/`, `src/.claude/` (source) ด้วย → **source หายจาก git**; ส่วน pattern ที่มี separator **กลาง** (เช่น `.claude/agents/`) git anchor to repo root ให้อยู่แล้ว (ไม่ leak src) — แต่ยัง **anchor `/` ทุกบรรทัดให้ explicit** เพื่อกันพลาด (ดู `docs/troubleshooting.md` #11). ตรวจด้วย `git check-ignore src/...` ว่า source ไม่โดน ignore เสมอ
- **regen dogfood ด้วย `npm run setup:dogfood`** (install release ลง root) · **test v-next ด้วย `npm run setup:sandbox`** (install `src/` ลง temp, ไม่แตะ root dogfood)
