# Rule — installer

> rule เฉพาะ component installer · rule ระดับโปรเจกต์อยู่ `docs/rule.md`

## โค้ด installer (`src/bin/cli.mjs`)
- **zero-dependency** — `src/bin/cli.mjs` ใช้เฉพาะ built-in (`node:fs`, `node:path`, `node:url`); ห้ามเพิ่ม dependency
- **ESM** — `import.meta.url` หา `pkgRoot`; ห้าม `__dirname`/`require`
- **★ ESM main-guard ต้อง realpath `argv[1]` ก่อนเทียบ `import.meta.url`** (ไม่ใช่แค่ `path.resolve`) — ESM `import.meta.url` เป็น **realpath เสมอ** (Node ESM loader resolve symlink) แต่ `process.argv[1]` เป็น path ตามที่ผู้เรียกระบุ (ไม่ resolve symlink). เทียบด้วย `path.resolve(argv[1])` จะ **mismatch → `main()` ไม่ถูกเรียก → installer เงียบ exit 0 ไม่ทำอะไร** เมื่อถูกเรียกผ่าน symlink — ซึ่ง **npx ทำเสมอ** (รัน bin ผ่าน `node_modules/.bin/<name>` symlink) และ `setup:dogfood` ทำ (extract tarball ลง `os.tmpdir()` ที่เป็น symlink บน macOS). แก้: pure-fn `export function isEntrypoint(argv1, metaUrl, realpath = fs.realpathSync)` → `realpath(argv1) === fileURLToPath(metaUrl)` + try/catch fallback `path.resolve` เมื่อ realpath throw (argv1 ไม่มีจริง); main-guard เรียก `isEntrypoint(process.argv[1], import.meta.url)`. **scripts อื่น** (`verify-pack`/`lint-md`/`setup-dogfood`) ใช้ guard ไม่ realpath ได้เพราะรันจาก npm-script (real repo path) — แต่ถ้าถูกเรียกผ่าน symlink ต้องใช้ pattern เดียวกัน — evidence: topic `fix-setup-dogfood-stale-payload` (root cause ชั้น 0 · `troubleshooting.md` TS-2 · `npx @warnyin/agents@0.18.0 --update` → 0 bytes ไม่สร้างไฟล์)
- **ห้าม copy พื้นที่ทำงานของผู้ใช้จาก repo ต้นทาง** — `docs/stages/` ต้อง generate scaffold เปล่าใน target (`ensureScaffold`) ไม่ใช่ `copyTree` จาก `pkgRoot` (กัน scaffold leak — `troubleshooting.md` #1)
- **ไม่เขียนทับงานจริง** — SCAFFOLD/seed/root docs ข้ามไฟล์ที่มีอยู่; `--update` เขียนทับเฉพาะ CORE
- **idempotent** — รันซ้ำต้องไม่พัง/ไม่ append ซ้ำ (CLAUDE.md/AGENTS.md มี marker `warnyin/workflow/stages/`)
- **legacy = เตือน ไม่ทำให้** — ตรวจโครงเก่าแล้วแนะนำคำสั่ง `git mv` ให้ user ทำเอง ไม่ย้ายงานจริงอัตโนมัติ
- **guard self-install = defensive no-op** — เก็บ guard `pkgRoot === target` ไว้ (zero-cost) แต่หลังย้าย source เข้า `src/` แล้ว `pkgRoot=src/` ไม่มีทาง === target (repo root/temp) → guard เป็น **no-op โดยตั้งใจ** (ยัง error เฉพาะ edge ที่ target===`src/` เอง) — comment ต้องตรงพฤติกรรมนี้ ห้ามลงทุน guard ใหม่
- **mirror layout `src/` = target paths** — โครงใน `src/` ต้องสะท้อน path ตอน install เป๊ะ (installer copy `src/<rel> → target/<rel>` ไม่มี mapping table); ฝืน invariant นี้ = ต้องเพิ่ม mapping → ขัดปรัชญากระทัดรัด — **global mode คง invariant นี้** (แค่ target=`os.homedir()` แทน cwd, rel path เดิม → `~/.warnyin/`, `~/.claude/`)
- **★ unconditional multi-IDE install (R2)** — installer ติดตั้ง adapter ทุก IDE (Cursor, Windsurf, Copilot, Cline, Gemini) พร้อมกันโดย**ไม่ detect** ว่า user ใช้ IDE ใด (zero-config) — การ detect IDE ทำให้ logic เปราะ + user ต้องรัน installer ซ้ำเมื่อเปลี่ยน IDE; feature ใน `docs/features/universal-ide/` — evidence: topic `support-universal-ide` (proposal §3 เลือก Option A explicit)
- **★ adapter-install-strategy convention (R1)** — adapter ที่อยู่ใน **directory เฉพาะของ IDE** (`.cursor/rules/`, `.windsurf/rules/`) ใช้ `installAdapterDoc({overwrite:UPDATE})` — `--update` refresh template ได้; adapter **top-level ที่ user อาจมีเนื้อหาก่อน** (`.clinerules`, `.github/copilot-instructions.md`, `GEMINI.md`) ต้อง **append-with-marker เสมอ ห้าม overwrite แม้ `--update`** — กันทำลายงาน user; evidence: topic `support-universal-ide` (task `add-ide-adapters/rule.md §2` + verify F1: fix `installAdapterDoc({overwrite:UPDATE})` branch)
- **★ global install mode = opt-in + ปลอดภัยต่อ homedir** (เขียนนอกโปรเจกต์ blast กว้าง) — มี mode `project` (default) / `global` (`--global`): (1) **opt-in** — ไม่ระบุ flag + non-TTY → `project` เสมอ (CI-safe ไม่ค้าง); prompt เฉพาะ TTY; **`resolveMode()` เป็น pure-fn** (unit-test ได้โดยไม่ spawn TTY); (2) **first-install `overwrite:false`** — ไม่ทับไฟล์ user ที่ชื่อชนใน `~/.claude/{agents,skills}/` (ทับเฉพาะ `--global --update` เจตนา); (3) **root doc = note-only append** — `installGlobalNote()` เขียน `~/.claude/CLAUDE.md` (personal global memory) แบบ append-with-marker `<!-- warnyin:global-note -->` **ห้ามเขียนทั้ง template/ห้ามทับ** (ใช้ helper แยก ไม่ reuse `installRootDoc` ที่เขียนทั้งไฟล์); (4) **homedir guard** — `os.homedir()` falsy/`===filesystem root` → error exit (กัน CI/container เขียนลง `/`); (5) **echo target paths** ก่อนเขียน (transparency blast นอก cwd) — evidence: topic `global-install` (cli.mjs + verify D1/D3/D7 executable; feature `docs/features/global-install/`)
- **★ resolution convention อยู่ root doc ไม่ใช่ทุก adapter** — กฎ "path `.warnyin/` หา local ก่อน fallback `~/.warnyin/`" เขียน **canonical ครั้งเดียว** ใน `CLAUDE.md`/`AGENTS.md`/`CLAUDE.global.md` (โหลด context เสมอ) — adapter (commands/skills) **ไม่ต้องแก้ path** (กัน duplicate 14 ไฟล์); per-project `CLAUDE.md` ต้องคง marker เดิม `warnyin/workflow/stages/` (idempotent guard) + `CLAUDE.global.md` (note-only) มี marker `<!-- warnyin:global-note -->`
- **template ระดับ feature/หน่วยผู้ใช้ ต้องอยู่ใต้โฟลเดอร์ `[...]` เสมอ** (seedDocs-skip invariant) — `seedDocs` ข้าม entry ที่ขึ้นต้น `[` เท่านั้น (`cli.mjs` seedDocs); วาง template ชื่อ concrete ใต้ `template/docs/` = seed leak ลง target จริง — evidence: topic `feature-spec-delta` (spec.md template ใต้ `[feature-name]/` + verify T2 negative: target ไม่มี `docs/features/` หลัง install)
- **★ scaffold-vs-seed ownership invariant — ไฟล์ที่มี template ห้ามอยู่ใน `SCAFFOLD_FILES`** — `main()` เรียก `ensureScaffold()` **ก่อน** `seedDocs()` และ seed เป็น skip-if-exists → ไฟล์เปล่าที่ scaffold สร้างไว้จะ **บล็อก template ตลอดกาลโดยไม่มี error** (false-green เงียบ: ผู้ใช้ได้ไฟล์ 0 byte ถาวร เคสจริงของ `docs/stages/context.md` รุ่นก่อน); ทิศเดียวกันที่ระดับ playbook — **bootstrap ต้อง seed-before-empty-fallback**: `/warnyin:init` ต้อง seed จาก template **ก่อน** แล้วสร้างไฟล์เปล่าเป็น fallback **เฉพาะเมื่อ template ไม่มี** (เดิมสร้างไฟล์เปล่าก่อน → seed ของตัวเองในขั้นถัดไป skip); เป็น invariant ที่ตรวจได้ด้วยเทส structural — evidence: topic `project-memory` (`design.md §6` + `installer.test.mjs` เคส seed/`--update`)
- **★ report-script ≠ gate-script** — script ใน `.warnyin/workflow/scripts/` ที่เป็น **รายงาน** (เช่น `memory-status.mjs`) ต้อง (1) **exit 0 เสมอ** (ถูกเรียกจาก playbook แบบ conditional — ต้องไม่มีทาง block งานผู้ใช้), (2) **ไม่พิมพ์เนื้อ artifact ออก stdout** — เฉพาะ metric/วันที่/flag (log เป็น surface ที่ข้อมูลอ่อนไหวหลุดได้) และไม่พิมพ์ absolute path ของเครื่อง, (3) มี **เคส negative-property ที่อ่านซอร์สตัวเอง** ยืนยันว่าไม่มี import ต้องห้าม (`child_process`/network) และไม่มี write API — ต่างจาก gate-script (`verify-pack`/`lint-md`/`check-test-count`) ที่ exit 1 เมื่อพบปัญหา — evidence: topic `project-memory` (T5 · verify V4.8/V4.9)
- **★ parser ของ template ต้อง row-based + เคารพ placeholder convention ทุกจุดที่ parse ไฟล์เดียวกัน** — (1) นับแถวตาราง markdown ด้วย **โครงของแถว** (คอลัมน์แรกเป็นตัวเลขล้วน) **ห้าม substring-match ทั้งบรรทัด** — legend/prose ที่ระบุ closed-set ในบรรทัดเดียวทำให้ตัวนับพองเงียบ ๆ; (2) **ห้ามใช้ `\w`/`\b` กับข้อความไทย** (ไม่ match); (3) **placeholder convention เป็นกฎระดับไฟล์ ไม่ใช่ระดับ field** — ถ้า template ใช้ HTML comment แทน "ยังไม่มีค่า" ต้องบังคับกับ **ทุก parser ที่อ่านไฟล์นั้น** ไม่ใช่เฉพาะจุดที่นึกออกตอนเขียน contract; (4) **★ fixture ต้องเป็นไฟล์ template ที่ shipped จริง และต้องมีเคส "ยังไม่เติม" เสมอ** (บังคับ ไม่ใช่ nice-to-have) — สองข้อคู่กัน: (ก) parser ที่อ่านค่าจาก artifact **ต้องถูกทดสอบด้วยไฟล์ template ที่ผู้ใช้ยังไม่เติม** — ถ้า parser คืนค่าที่ "ดูใช้ได้" จากโครงเปล่า แปลว่า gate จะ**เงียบทั้งโปรเจกต์** (ไม่ ✖ ไม่ ⚠ — default state ของ template กลายเป็นค่าที่ถูกต้องโดยบังเอิญ); (ข) fixture ของ heuristic ที่ตัดสิน "artifact เริ่มเติมหรือยัง" ต้อง **อ่านไฟล์ template จริงมาใช้** ไม่ใช่ string ที่ผู้เขียนเทสแต่งขึ้น — fixture ประดิษฐ์เองพิสูจน์แค่ว่า "โค้ดตรงกับจินตนาการของผู้เขียน" (เทสเขียวแต่ของจริงหลุด 100%); + ตรวจ regression กับ **artifact จริงทุกใบ** ก่อนสรุปว่ากฎ parse ใหม่ปลอดภัย — evidence: topic `project-memory` (panel QA-B3 + **KB TS-5**: `findLastUpdated` พิมพ์ comment ดิบตอน fresh install ทั้งที่ unit+structural เขียวหมด) · topic `lean-ceremony` ([TS-1](../../stages/achieved/2026-08-16-lean-ceremony/troubleshooting.md): `parseTier` คืน `fast` จากแถว template ⇒ C7 ปิดตัวเองเงียบทั้งโปรเจกต์ · TS-2: fixture D6/D7 ที่เขียนเองไม่ตรง §4 ของ template จริง 28 บรรทัด ⇒ เทสเขียวแต่ทุก topic ยังกระโดดเป็น VERIFY)
- **★ `MIN_PASS` ของ pass-count gate ต้อง bump พร้อม topic ที่เพิ่มเคส + คอมเมนต์ระบุที่มาของตัวเลข** — ค่าที่ตกยุค (46 ขณะยอดจริง 151) ทำให้ gate หลวมจนตรวจไม่เจอกรณี **ไฟล์เทสหายทั้งไฟล์/ไม่ถูก discover** (`pass === tests` ยังเขียวได้) — bump ให้ใกล้ยอดจริง (เว้น headroom) และเขียนที่มาไว้ในคอมเมนต์เพื่อให้ topic ถัดไปรู้ว่าต้องขยับ — evidence: topic `project-memory` (T6 bump 46 → 180 จาก N=192)
- **template ระดับ stage ที่ห้ามติด whole-folder copy → วางนอก `[topic]/` (top-level ใน `template/stages/`)** — คู่ทิศกลับของ seedDocs-skip invariant: template ใต้ `[topic]/` ถูก copy ทั้งโฟลเดอร์ทุกครั้งที่เปิด topic → ไฟล์ที่ต้อง copy **แบบเลือกเอง** (เช่น `receipt.md` ของ fast tier) ต้องอยู่นอกโฟลเดอร์ที่ถูก copy เหมา ไม่งั้นทุก topic ติดไฟล์นั้นไปด้วย (validator ตีความ mode ผิด) — evidence: topic `build-lean` design review SA B1/QA B3 → `template/stages/receipt.md` อยู่นอก `[topic]/` + installer.test assertion คุ้ม

## 2. Error category + scanning patterns (L: topic `publish-pack-polish`)

- **★ error string ของ gate script ต้องมี category prefix** (`eol:` / `path:` / `denylist:` / `allowlist:` / `tripwire:` / `R1:` / `R2:`) — เพื่อ (1) test assert ได้ด้วย grep prefix (แทน substring ทั้งประโยค), (2) maintainer/contributor อ่านง่าย รู้หมวดทันที, (3) runbook อ้าง prefix เป็น identifier ได้ — evidence: topic `publish-pack-polish` (Slice A error contract: `eol:` + `path:` + existing denylist/allowlist/R1/R2/tripwire — prefix convention generalize ทุก gate)
- **★ Buffer-level byte check ก่อน UTF-8 decode สำหรับ byte-pattern scan** — `buf.includes(0x0D)` เร็วกว่า `text.includes('\r')` + กัน false-positive จาก multi-byte codepoint ที่อาจมี 0x0D เป็น byte หนึ่ง — pattern ใช้ซ้ำได้กับ BOM/control char scanner อื่น — evidence: topic `publish-pack-polish` (Slice A checkEol: Buffer-level)
- **★ size cap pattern สำหรับ I/O bulk scan** — `opts.maxBytes` (default 5 MB) + `entries[].buf = null` + `console.warn(...)` — **ไม่ throw** (gate robust — dev ไม่ติด false-green) — pattern: `entries.push({path, buf:null, ext})` + log; กัน DoS + false-positive จากไฟล์ที่มี byte pattern legitimately (เช่น binary ฝัง CR) — evidence: topic `publish-pack-polish` (Slice A readTextEntries)
- **★ importable constant pattern ระหว่าง layers** — shared constant (เช่น `TEXT_EXT`) export จาก module ที่เป็น **canonical owner** (เช่น `cli.mjs` ที่ใช้ใน `normalizeEol`) + import ที่ module อื่น (`verify-pack.mjs`) — เงื่อนไข: (1) module ผู้ส่งออกไม่ import จาก module ผู้ใช้ (no circular), (2) constant เป็น immutable `Set`/`const` ไม่ mutate, (3) zero-dep (built-in เท่านั้น) — กัน DRY drift ระหว่าง layers ที่ share config — evidence: topic `publish-pack-polish` (Slice A TEXT_EXT: cli.mjs export + verify-pack import)
- **★ negative-grep regression pattern สำหรับ wording fix** — เมื่อเปลี่ยน substring (เช่น `--help` text) test ต้อง assert **substring เก่า `NOT includes`** ไม่ใช่แค่ substring ใหม่ `includes` — กัน regression เงียบที่ substring เด้งกลับโดยไม่มีใครสังเกต — evidence: topic `publish-pack-polish` (Slice B spawn test: `!stdout.includes('ไม่แตะ docs/')` + `stdout.includes('เขียนทับเฉพาะ CORE')`)
- **★ spawn test pattern สำหรับ CLI text** — `--help`/`--version`/user-facing text → เพิ่มเคส spawn `process.execPath + [cliPath]` → `assert stdout.includes(newSubstring) && !stdout.includes(oldSubstring) && code===0` (regression guard); **ไม่พึ่ง grep source** (อ่านผ่าน CLI contract ตรง ๆ) — evidence: topic `publish-pack-polish` (Slice B installer.test: 1 เคสใหม่)
- **★ Migration section executable proof required** — CHANGELOG "Migration guide" ทุก section ที่มี **คำสั่งที่ผู้ใช้รัน** ต้องผ่าน sandbox test (คำสั่งทำงานจริง) + **warn destructive command** (เช่น `git reset --hard` ลบงานค้าง) — pattern เดียวกับ `troubleshooting.md` #10 migration verification — evidence: topic `publish-pack-polish` (Slice C acceptance: sandbox + intentional CRLF + renormalize + verify:pack ผ่าน)
- **★ BUILD agent checklist ต้องรวม "Spec delta applied ลง feature spec"** — apply ลง `docs/features/<name>/spec.md` (ADDED ต่อท้าย · MODIFIED แทนที่ · REMOVED ลบ) **ก่อน** รายงาน passed; unit/lint green **ไม่พอ** (เป็น doc gate — ต้องมีใน acceptance ของ BUILD task) — evidence: topic `publish-pack-polish` (VERIFY Finding 2: BUILD ลืม apply 11 Scenarios ลง installer-version-stamp/spec.md — จับตอน VERIFY)

## 3. Cross-platform `verify-pack` Windows support (L: topic `publish-pack-polish` — supersede `troubleshooting.md` #4)

- **★ `getNpmCmd(platform)` — Windows dev ใช้ `process.execPath + npm_execpath` ไม่ใช้ `.cmd`** — pure fn `getNpmCmd(platform = process.platform)`:
  - `win32` + `process.env.npm_execpath` ตั้ง → `{ bin: process.execPath, prefix: [npm_execpath] }` (`main()` spawn `node <npm-cli.js>` ตรง ไม่ผ่าน shell)
  - `win32` + no `npm_execpath` → `null` (`main()` exit 1 + error "ต้องรันผ่าน `npm run verify:pack`")
  - `darwin`/`linux` → `{ bin: 'npm', prefix: [] }`
  - **ปิด 2 ปัญหาในที่เดียว:** (1) **CVE-2024-27980** — Node ≥20.12.2 reject `.cmd`/`.bat` ด้วย `shell:false` (EINVAL); (2) **PATH/CWD hijack** — unqualified binary name + symlinked cwd = supply-chain surface
  - **supersedes `troubleshooting.md` #4** (เดิม: ยอมรับเป็น dev-only + Windows workaround — แก้แล้วด้วย pattern นี้)
  - test `getNpmCmd` × 3-4 เคส (darwin/linux/win32-with-path/win32-no-path)
  - evidence: topic `publish-pack-polish` (Slice A `getNpmCmd` + 4 unit tests + main() refactor)

## 4. Validator ระดับ topic + release sweep ของ payload (L: topic `lean-ceremony`)

## packaging / publish
- **`package.json files` เป็น allowlist (granular)** — เพิ่ม path ต้องพิจารณา publish; **dotfolder nested ต้องระบุชัดทุกก้อน** (`src/.warnyin`, `src/.claude/commands`, `src/.claude/agents`) — npm ไม่รวม nested dotfolder อัตโนมัติ (บทเรียน 0.6.0 ขยายผล); งานจริง (`docs/`) + dev tooling (`src/tests`/`src/scripts`) ห้ามหลุด
- **pack-verify เป็น gate ก่อน publish + ต้อง testable** — แยก pure function `checkFiles(files)→errors[]` ออกจาก `npm pack` มี unit ป้อน file list ปลอมพิสูจน์ denylist จับได้ (กัน "gate ลวง" ที่เขียวเพราะ allowlist ปิด ไม่ใช่ denylist ทำงาน); assert payload ติดครบ (`src/.warnyin/workflow/` **และ** `src/.claude/commands/warnyin/`)
- **denylist ต้องครอบ dogfood ที่ root + tripwire** — bootstrap layout ทำให้ installed payload (`^.warnyin/`, `^.claude/`, root `CLAUDE.md`/`AGENTS.md`) เสี่ยงหลุดขึ้น package เอง → denylist ต้องจับ + tripwire (`settings.local.json`, `*.tgz`, `.env*`)
- **registry-target ของ root dogfood file = installer template ไม่ใช่ root** — `CLAUDE.md`/`AGENTS.md` ที่ root เป็น **dogfood install (gitignored, not tracked)**; canonical ที่ ship จริง (slash-command list ที่ผู้ใช้ปลายทางเห็น) อยู่ `src/.warnyin/installer/templates/CLAUDE.md` (ใน `package.json files`) — ก่อนแก้ registry/slash-command list ที่ root **เช็ค `git check-ignore <file>` ก่อนเสมอ**: ignored = dogfood → แก้ที่ `src/.warnyin/installer/templates/` (extends `docs/troubleshooting.md` #18 root-dogfood-gitignored, #22) — evidence: topic `feedback-issue-command` (TS-1 + build.md §3 — agent แก้ root CLAUDE.md → ไม่ติด commit; orchestrator redirect ไป template)

## build orchestration (`build-wave.mjs`)
- **worktree base ปนเปื้อน → cherry-pick commit เดี่ยว ไม่ merge ทั้ง branch** — harness fork worktree จาก base ที่คุมไม่ได้ (อาจคนละสายกับ build branch) → ตอน integrate ผล wave ถ้า branch ของ agent ต่อยอดบน base ผิด/ปนเปื้อน ให้ `git cherry-pick <commit เดี่ยวของ agent>` (เอาเฉพาะ diff ไฟล์ที่ task own — file-ownership disjoint การันตีไม่ชน) **ห้าม `git merge` ทั้ง branch** (ลาก divergence ของ base เข้ามา)
- **worktree sync เชื่อถือไม่ได้ → fallback `isolate:false` (shared-tree)** — ถ้า root script stale/ขาด `baseRef` (sync-gap, `docs/rule.md` §1 build-orchestration) → รัน shared-tree: agent ทำใน working tree จริง (เห็น root `.warnyin/`+docs/+src/ ครบ) main loop commit ให้; เสีย parallelism ใน wave แต่ได้ correctness (file-ownership disjoint → sequential ก็ปลอดภัย) — evidence: topic `improve-performance` (build.md §3 integration notes — wave 1 worktree fail → cherry-pick 2 task + shared-tree re-run failed task + wave 2)
- **★ payload workflow script ห้าม top-level `export` นอกจาก `export const meta`** — `build-wave.mjs` (และ script ใด ๆ ใน `.warnyin/workflow/scripts/` ที่รันผ่าน **Workflow tool**) ถูก harness wrap ที่ยอมรับเฉพาะ `export const meta` (ตัวบังคับ); **`export function`/`export` อื่นทำให้ Workflow loader พังด้วย `SyntaxError: Unexpected keyword 'export'`** — ถ้าต้องการ pure-fn ให้ unit test ใช้ ให้ test **สกัดด้วย module-parse/`new Function`** (pattern `docs/troubleshooting.md` #16) หรือย้าย pure-fn ไป helper แยกที่ test import ได้โดยไม่กระทบ workflow script — **ห้าม `export function` ในตัว workflow script เอง**; workaround ชั่วคราวตอนรัน = temp copy ที่ `sed 's/^export function /function /'` (คง `export const meta`) **หรือ** fan-out ผ่าน Agent tool โดยตรง (build.md §6 fallback — คง worktree+parallel+model ได้) — evidence: topic `global-install` (`troubleshooting.md` TS-1/#20 + build.md §5) + เจอซ้ำครั้งที่ 3 topic `parallel-design-docs`. **✅ fix ถาวรแล้ว (topic `build-wave-export-fix` · 2026-06-11):** `build-wave.mjs` ไม่มี `export function` แล้ว (เหลือ `export const meta`) + inline comment guard กัน re-add — Workflow launch ผ่าน (proof run `wf_4898135a-19c`); follow-up = lint-gate ตรวจ `^export function` อัตโนมัติ (`docs/roadmap.md` #12)

- **prompt ของ workflow script ต้องมี unit test คุ้ม contract** — `prompt()`/instruction-builder ใน `.warnyin/workflow/scripts/*.mjs` เป็น contract ที่ agent ปลายทาง execute ต่อ ต้องมีเทสทั้ง **เชิงบวก** (สิ่งที่ agent ต้องถูกสั่งให้อ่าน/ทำ — role card, ไฟล์ task, conditional step) และ **เชิงลบ** (เอกสารที่ตัดออกแล้วต้องไม่โผล่กลับ) ด้วย extractFn + `new Function` (KB#16; template literal ที่อ้างตัวแปร module-level → inject เป็น parameter ของ factory — KB TS-2 build-lean) — ไม่งั้น reading-list bloat regress กลับได้เงียบๆ โดย suite เขียว — evidence: topic `build-lean` (prompt lean + เคส F-K ใน `build-wave.test.mjs` — ก่อนหน้านั้น prompt ไม่มี test คุ้มเลย)

## dev tooling (`src/scripts/setup-*.mjs` — bootstrap/dogfood)
- **npm scripts (`setup:*`) ต้องเป็น node script cross-platform** — zero-dep/ESM ใน `src/scripts/`; ใช้ `os.tmpdir()`+`mkdtempSync` (ห้าม hardcode `/tmp`), `path.join`; spawn array args **ห้าม `shell:true`** ยกเว้นเรียก npx บน win32 (`.cmd`); ต้องมี fallback (npm pack→extract→node) หรือ exit ด้วย error ชัดเจน (ห้าม false-green)
  - **★ verify side-effect ไม่เชื่อ exit 0 + ส่ง flag ตรงเจตนา** (enforce ของ "ห้าม false-green") — dev-tooling ที่ spawn external install (`npx`/`npm`) **ต้องตรวจ side-effect จริงหลังรัน** (เช่น `verifyInstalled(root)` เช็ค CORE markers `.warnyin/workflow/stages/discovery.md` + `.claude/commands/warnyin` exists) **ไม่เชื่อแค่ `r.status===0`** — `exit 0` เกิดได้โดยไม่ install จริง (npx bin resolution เพี้ยน) → false-green แม้มี fallback (เพราะ success-detection คืน true ก่อน fallback); และ **ส่ง flag ให้ตรงเจตนา** (`setup:dogfood` ต้องส่ง `--update` ไม่งั้น cli `copyTree({overwrite:false})` ข้าม CORE เดิม → ไม่ refresh); pure-fn `verifyInstalled` **export + main-guard** (testable, เคส partial→false พิสูจน์ guard) — evidence: topic `fix-setup-dogfood` (`troubleshooting.md` #21 + verify V1-V6; เจอจริงตอน release 0.15.0 ของ `discovery-mode-selector`)
    - **★ verify เทียบ "ค่า version" ไม่ใช่แค่ existence ของ marker (LR1 — ขยายผลของ "verify side-effect")** — marker-existence จับ "ไม่ install เลย" ได้ แต่ **จับ "install เวอร์ชันเก่า" ไม่ได้** (npx cache ส่ง payload เก่า → marker ครบ → false-green รอบ 2 / issue #3). root cause = payload ไม่มี **version identity**. แก้: (1) installer เขียน **version stamp** (`.warnyin/.warnyin-version` = `package.json` version, unconditional overwrite ทุก install/`--update`, install-time artifact ไม่ขึ้น tarball); (2) `verifyInstalled(root, expected)` เทียบ **ค่า stamp** กับ expected (normalize trim สองฝั่ง กัน CRLF); (3) **expected resolver** = `npm view` + `parseNpmViewVersion()` **pure fn** (parse บรรทัด semver จริง ทน notice/warning ปน stdout → testable ไม่ต้อง spawn) + **degrade graceful + warn loud** เมื่อ fail (offline = install เองก็ fail); (4) **stale-cache defeat = pin exact version** (`@<ver>` แทน `@latest` เลี่ยง dist-tag cache mapping เก่า = ตัวหลัก) + `npm_config_prefer_online` (เสริม), **ส่ง expected เข้า verifyInstalled ทั้ง npx + pack path** (กัน drift ตายเงียบบน pack/Windows) — evidence: topic `setup-dogfood-version-check` (issue #3 · design §4B truth table · verify T4 drift→false จริง; feature `docs/features/installer-version-stamp/`)
    - **★ bootstrapping transition-safe — feature ที่ verify ด้วย artifact ที่ตัวเองสร้าง (LR2)** — เมื่อ verify พึ่ง artifact ที่ feature เดียวกันเป็นคนสร้าง (เช่น stamp) จะมี **transition window**: release/รุ่นเก่าที่ยัง**ไม่มี** writer → artifact ขาด → **ต้องไม่ false-fail** (degrade marker-only + warn, ไม่ block). ตัวจับจะ **active เต็มตัวตั้งแต่ release ที่ 2** ที่มี artifact เป็นต้นไป (รุ่นแรกพึ่งกลไกอื่นกัน edge — เช่น pin-exact/prefer-online กัน stale). **VERIFY/SHIP ต้องบันทึก snapshot ตามจริง** ว่ารอบไหนเริ่มจับได้ — ห้ามเคลม "จับได้ทันที release นี้" — evidence: topic `setup-dogfood-version-check` (design §6 + verify snapshot: registry `@latest`=0.16.0 ยังไม่มี stamp → transition true)
      - **✅ LR2 implemented (topic `fix-setup-dogfood-stale-payload` · 2026-06-13):** `verifyInstalled` stamp ขาด → `semverGte(expected, '0.17.0')` → false (active — install ผิด/payload เก่า); expected < 0.17.0 หรือ non-semver → true (transition/degrade-safe). active เต็มตัวตั้งแต่ release ที่ 2 (0.17.0 = release แรกที่มี stamp writer) — `STAMP_MIN_VERSION='0.17.0'` constant + pure `semverGte(a,b)` (numeric tuple, NaN→0). registry snapshot ตอน ship: `@latest`=0.18.0 มี stamp แล้ว → active path ทำงานจริง
- **★ dev-tooling fallback path ต้อง symmetric กับ primary path** — cache-bust / version-verify guard ที่อยู่ใน primary path **ต้องมีครบใน fallback path ด้วย**. `installViaPack` (fallback) เคยขาด `npm_config_prefer_online` ที่ `installViaNpx` (primary) มี → fallback ดึง stale tarball ได้ทั้งที่ primary กันแล้ว = false-success regression (รอบ 3 ของ setup-dogfood). guard ทุกชั้น (pin-exact, prefer-online, version-check ที่ source, verifyInstalled) ต้อง apply สมมาตรทุก install path — evidence: topic `fix-setup-dogfood-stale-payload` (proposal §3 ชั้น A · design §4 `installViaPack` 2 fix)
- **`setup:dogfood` เตือน review payload diff ก่อนเปิด session** — payload ที่ install จาก `@latest` ถูก agent execute ต่อ = supply-chain surface (low risk เพราะ release ตัวเอง แต่ comment เตือนเป็น policy)
